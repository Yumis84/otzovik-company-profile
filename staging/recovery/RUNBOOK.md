# Восстановление baseline Specialist MVP

Единственная цель — Supabase salmcnhexlftrgtiryyo. Сверить ref в консоли и hostname подтверждённого TLS-соединения до любых операций. Доступ к production не нужен. Использовать проверенный release.zip целиком. Отдельные исторические SQL, включая 20261122, самостоятельно не исполнять.

## Фактическая исходная точка
PostgreSQL 17.11. Семь профилей, две строки specialist_media, обе сопоставлены с объектами правильного MIME и размера, всего три приватных объекта. Третий объект без зарегистрированной строки сохраняется. Включён FORCE RLS на семи таблицах. Снимок фиксирует 17 тел функций и ACL, семь политик storage.objects (в том числе четыре политики компании). Функция Edge, getter, таблицы публикации, профильная версия, резервации и роль specialist_operator изначально отсутствуют.

postgres имеет BYPASSRLS, CREATEROLE и права на таблицы профилей. Он не владеет storage.objects и не может переключиться в supabase_storage_admin. Обычное подключение postgres получит отказ до DDL. Нужен предусмотренный платформой оператор, уже уполномоченный выполнять обе группы DDL в одной транзакции. Не расширять membership postgres и не извлекать системные учётные данные. Если такой путь не предоставлен, остановиться. Другие предпосылки: рабочий частный preview, возможность отката его предыдущей версии, проверенные резервная копия БД и способ сохранения содержимого приватного бакета, окно остановки всех writers, две синтетические Auth-сессии и доступ к журналам Edge/Storage. Они не входят в SQL-пакет.

## Последовательность после отдельного OWNER GO
1. Проверить SHA256SUMS, baseline-check.sql и hosted-storage-check.sql в сессии только чтения с обычным search_path публичной схемы. Повторить список Edge Functions и проверку владельцев. Сохранить baseline, исходную приватную версию frontend и настройки. Проверить отсутствие конкурирующих миграций. Согласовать возвращаемый старым клиентам срок обслуживания. До переключения действуют прежние правила прямой записи. Одновременная поддержка прямых записей и новых резерваций нарушила бы учёт.
2. Остановить загрузку, удаление и регистрацию фото всеми клиентами и фоновыми заданиями. Дождаться завершения открытых запросов и подписанных операций Storage. SQL-lock сам по себе не останавливает внешний HTTP Storage. Сверить агрегаты заново. Не удалять бесхозный объект. Не принимать публикацию существующих записей по умолчанию.
3. Выполнить 01-install.sql целиком с остановкой при первой ошибке. Исходные SQL собраны без промежуточных COMMIT. Существующие таблицы редактора не пересоздаются. Функции приложения принадлежат postgres, только Storage policy DDL исполняется от владельца Storage. Три ограничительных политики запрещают прямые записи в specialist-media. Новый operator NOLOGIN не получает идентичностей автоматически. Старые зарегистрированные фото получают ready-резервацию без выдуманного fingerprint. Новые функции и таблицы закрываются согласно проверенной матрице. Публичная выдача и новые записи медиа пока выключены.
4. Поставить поставляемый specialist-media-gateway только в указанном проекте. Указать один разрешённый origin закрытого preview. Сохранить текущую модель JWT, секреты держать только на сервере. Доказать на Edge, что запрос к закрытой фотографии не отдаёт байты, а гостевой apikey не позволяет owner-операций. Проверить ограничения ingress, rate limit и размер ответа Storage. При несовместимости остановить переключение. frontend/staging.zip разместить только как закрытую версию. SDK локален. Публичная в контексте Auth страница остаётся за внешней защитой preview.
5. Выполнить 02-enable-media.sql, затем 03-enable-public.sql после проверки отсутствия ранее опубликованных записей. На двух синтетических пользователях выполнить create/save/reload/relogin, чужой UUID, услуги, выбранные контакты, upload/delete, публикацию и unpublish. Проверить журнал сетевых обращений, зачистить только известные тестовые ID после сохранения доказательств. Завершать maintenance после проверки новой клиентской записи. Старые клиенты прямой записи должны перейти на gateway.

## Возврат к исходной точке
Остановить frontend-записи, 80-quiesce.sql и внешних writers. Удалить созданную на этом этапе Edge Function только после сверки исходного пустого списка и завершения текущих запросов. Восстановить предыдущую приватную сборку. Разобрать uploading/deleting и erasing по исходным идентификаторам, без массового удаления. До открытия старых клиентов завершить SQL-откат.

Сохранить данные добавленных rollout-таблиц, в том числе историю публикации и аудита, и версии профилей во внешнем зашифрованном хранилище владельца. Выполнить archive-query.sql через psql -XAtq с client_encoding UTF8 и локальным перенаправлением вывода в защищённый файл, umask 077. Скрипт verify-archive.py проверяет форму, порядок и SHA256 архива и печатает контрольную сумму для otz.recovery_archive_digest. Подтвердить возможность чтения копии с резервного носителя. Установить этот digest как session setting в той же операторской сессии перед 90-rollback.sql. Никогда не публиковать экспорт строк в Hub. Сверка под блокировками отменит откат при расхождении. MD5 здесь служит проверкой согласованности экспортированных строк, SHA256 — контролем самого файла. Исходные таблицы и storage.objects не удаляются и не заменяются. Персональные данные, удалённые пользователем во время эксплуатации, не восстанавливаются из старой копии.

90-rollback.sql атомарно убирает добавленные RPC, таблицы, роль и триггеры, возвращает исходный delete RPC, статус профиля, legacy grants и политики. Новые ревизии и история сохраняются во внешнем архиве. При неожиданных зависимостях DROP без CASCADE завершится отказом. После commit проверить baseline-check.sql, hosted-storage-check.sql, отсутствие Edge и getter, возможность чтения и прямой записи владельцем синтетического профиля и сохранность файлов. Полный snapshot до перехода — аварийный резерв, восстановление поверх чужих изменений требует отдельного решения.

## Доказательства и ограничения
Тест tests/staging-recovery.mjs проверяет сборку под PostgreSQL 17.11 и PGlite на синтетических строках, загружает 17 полученных из staging определений, семь исходных политик, имитирует storage metadata и две учётные записи. Заглушки вспомогательных функций политик компании не воспроизводят managed Storage, байты файлов и hosted Auth. Равенство снимков до/после проверяется для функций, прав, политик, триггеров, таблиц, профилей и метаданных фото. Реальные E2E и ingress требуют этапа 2. Отдельные риски аудита Claude: квоты гостевой выдачи, доверие к Content-Length Storage, параллельные writers. Не выдавать разрешение на открытие preview внешней аудитории.
