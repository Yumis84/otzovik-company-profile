# Disposable operation journal prototype

This is an isolated test fixture, not a deployed issuer, recovery service, or authorization grant. A validated synthetic token reserves a PostgreSQL row keyed by jti before the simulated action. A separately generated recovery capability is hashed in that row. Within one transaction the simulated action and the `done` state commit together. Concurrent duplicate calls serialize on the row. A retry while the token remains valid reads the already committed result; status via the recovery capability remains available after token expiry or an epoch bump. A `reserved` row is `pending_or_unknown` and never authorizes retry: absence of an outcome is not proof that an operation stopped. The `loseReply` switch throws only after COMMIT returns to the process; it is not a network interruption, crash test, or proof of provider-authoritative recovery. Recovery capability delivery, secure storage, authenticated callers, rotation, retention, revocation, availability, tamper resistance and provider transaction guarantees remain unimplemented. Prototype cannot be attached to runtime.

The earlier token-based status is intentionally limited to unexpired tokens with unchanged active epoch; it cannot recover later. The anonymous denial audit aggregates by reason and minute, with no token or identity fields; this bounds rows per minute, not total storage or traffic. A real service needs traffic limits, retention and audit failure alerts. When audit fails, the originating denial is preserved and annotated, but action remains denied.

## Shared execution and unresolved pending outcomes

A reservation blocks the legacy consume path, and a pre-existing consumption blocks reservation; subject-row locking serializes these decisions. Both simulated action paths use the same consumptions jti primary key and actions table. The journal action and its outcome commit together. Rollback of an action leaves the reservation intact, and explicit subsequent calls are test-only; `pending_or_unknown` itself never schedules or authorizes a retry or cancellation. Recovery uses a global per-minute synthetic budget, including successful attempts. This deliberately simple global limiter can deny legitimate callers under load; it is not a real distributed rate limiter or an identity-based defense. Secret syntax and simple diversity checks do not prove entropy; test callers generate 32 random bytes. The first valid reservation binds the secret and ownership, so a stolen token can preempt the rightful caller; real authenticated reservation and secure capability delivery remain open.

**OWNER DECISION REQUIRED — pending after expiry or unknown COMMIT:** options include (1) retain pending and require a human to consult authoritative provider evidence, (2) retry only after an authoritative idempotency/termination guarantee, or (3) cancel only with a confirmed fence and provider evidence. All require provider-specific mechanisms; an arbitrary timeout alone proves neither cancellation nor absence of a committed action. Choice, evidence, escalation, retention and operator authority remain undecided. No automatic retry or cancellation is implemented.
