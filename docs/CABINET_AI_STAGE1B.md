## Atomic apply and full-replacement RPC correction

The existing company RPC replaces name/description/website/phone/city/email and has no expected-version parameter. A browser pre-read would race and could erase unrelated fields. cabinet_apply_proposal instead locks the profile in the database and checks the SHA256 canonical JSON of TOUCHED fields. It reads all current values under that lock, overlays validated description/city only, and calls existing update_my_company_profile within the SAME transaction. Its existing validation, live role checks and audit behavior are reused; no duplicate validator body or changed signature. The remaining five fields come from the locked current row, not model/client state. This is the common-writer reuse variant of Claude's preferred DB-RPC design, without refactoring the existing production RPC.

Apply accepts server proposal ID, expected base hash, explicit confirmed=true, and optional edits whose field set MUST equal the stored allowed set. No model-supplied target/base/status can be accepted. 1500char description and120city cap (conservative relative to existing2000/120). Values NFC-normalized; control/bidi stripped, HTML tags rejected. Proposal locks/profile advisory lock make double apply once-only. User edits cannot introduce contact/name/status/slug fields.

On a stale touched field, proposal status becomes superseded and HTTP409 is returned using transaction-scoped response.status, WITHOUT raising an exception that would roll back the status change. PostgREST commits non-failing transactions; see https://postgrest.org/en/stable/references/transactions.html#response-status-code . Repeated successful apply returns stored result without another write/audit. Existing editor full replacements from stale OTHER tabs remain an existing limitation of that RPC; assistant applies are atomic and test checks manual-save-before-apply. Launcher refuses apply while the local editor has unsaved changes and reloads it after apply.
