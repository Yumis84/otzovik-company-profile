# PR #17 — приёмка приватных черновиков специалистов

Дата: 17 октября 2026, Europe/Kaliningrad. Репозиторий: `Yumis84/otzovik-company-profile`, ветка `feature/profile-kind-chooser-v1`. Исходный HEAD: `76311db`. Production не изменялся.

## Решение

Реализован этап **самостоятельный специалист / мастер: создать приватный черновик → увидеть в кабинете → открыть → изменить**. Форма и серверные SQL-кандидаты готовы к согласованному развёртыванию после зелёного CI на итоговом HEAD и контрольных условий ниже. Это не заявление о работе функции в production: на момент проверки там нет ни таблицы специалистов, ни трёх RPC.

Публичные профили, услуги, фото, отзывы, привязка сотрудника к компании, чаевые/баланс и MCP остаются отдельными этапами. Для специалиста нет обходного создания через компанию. Существующее поведение компаний `active/ready` сохранено; их жизненный цикл этим PR не переделывается.

## Исправленные проблемы

| Проблема | Исправление |
|---|---|
| SELECT по companies не исключал конкурентную регистрацию одинакового адреса | Общая `profile_slug_registry` с PRIMARY KEY; AFTER-триггеры на INSERT/UPDATE slug/DELETE обеих таблиц. Индекс арбитрирует транзакции, включая старые company writers |
| Не учитывался обратный конфликт — компания после специалиста | Company RPC получает unique violation из реестра и сохраняет прежнюю логику суффиксов |
| DNS-метка могла достигнуть 64 символов | 3–63 символа в форме/RPC, усечение основы перед суффиксом, ограниченный цикл повторов |
| Сайт по умолчанию оставался на исходном занятом адресе | Формируется сервером по фактически выделенному slug; явный внешний сайт сохраняется |
| Репозиторный старый SQL терял production-проверку дубликатов компаний | Новый кандидат основан на прочитанной production-функции; проверка сайта / название+город, membership и audit сохранены |
| `get_my_companies` показывал revoked/suspended membership | Только `verification_status='verified'`; auth и формат ответа сохранены |
| Создание/редактирование/форма расходились в пределах полей | Имя 2–150, профессия обязательна 1–120, специализация ≤160, город ≤120, описание ≤2000; ограничения также в таблице |
| Специалист без компании после входа попадал в создание нового профиля | Вход возвращает в кабинет либо разрешённый `next`; регистрация ведёт к выбору типа |
| При входе терялся id редактируемого профиля | Полный относительный `next` с id; неавторизованная форма не вызывает RPC |
| Ошибки загрузки могли скрываться как пустой список | Независимые сообщения для компаний/специалистов; успешная часть списка остаётся видимой |
| Незагруженный/чужой черновик и повторное нажатие сохранения | Поля заблокированы до загрузки собственного draft; проверка UUID; защита повторного submit; понятные ошибки, значения остаются в форме |

Тестовая auth.uid использует session GUC, как интерфейс claims для SQL. Она не проверяет JWT/почту. Браузерный адаптер проверяет точные имена/параметры RPC и исполняет SQL, но не воспроизводит HTTP PostgREST. Существующий внешний publisher заменён sentinel; реальная отправка никогда не запускалась. Fixture включает необходимые таблицы/constraints, но не всю production-схему и её политики. Никакие production записи/секреты не скопированы.

Read-only Supabase: 7 компаний, нормализованных конфликтов slug — 0, меток длиннее 63 — 0, specialist table/RPC — отсутствуют. Владелец текущих company RPC — postgres с BYPASSRLS. Штатный company publisher-триггер привязан к UPDATE companies, не к специалистам. Точные прочитанные определения двух company RPC сохранены в `tests/fixtures/company-rpcs-before.sql` для сверки, а не для слепого отката.

Hub проверен: отдельного актуального PROJECT_STATE для этой ветки, AGENTS.md и WORKSTREAM_SCOPE.md в доступной shared memory не найдено; в репозитории этих файлов тоже нет. Scope взят из прямого задания владельца, Issue #19 и последних Hub событий. Клоду отправлен запрос независимого review; его новый PASS не заявляется до получения ответа.

## Повторение тестов

```sh
npm ci --ignore-scripts
npm test
npx playwright install chromium
npm run test:browser
```

Без `TEST_DATABASE_URL` используется in-memory PGlite, и настоящая многосессионная конкуренция явно SKIP. Для неё CI запускает одноразовый PostgreSQL 16. Локальный PostgreSQL допустим только на loopback, база `otzovik_acceptance`; harness отказывается от удалённых адресов. Нужна пустая тестовая БД, не production. При наличии установленного Chromium можно задать `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`.

## Недеструктивный откат

При сбое frontend вернуть предыдущий согласованный release страниц, убрать вход в создание специалиста. БД/черновики/реестр не удалять: сохранённые адреса должны оставаться занятыми, данные владельцев — сохранёнными.

Если необходимо временно отключить backend специалиста, после отдельного разрешения выполнить:

```sql
BEGIN;
REVOKE EXECUTE ON FUNCTION public.create_my_specialist_draft(text,text,text,text,text,text) FROM authenticated;
REVOKE EXECUTE ON FUNCTION public.get_my_specialists() FROM authenticated;
REVOKE EXECUTE ON FUNCTION public.update_my_specialist_draft(uuid,text,text,text,text,text) FROM authenticated;
NOTIFY pgrst, 'reload schema';
COMMIT;
```

Этот откат проверяется тестом: specialist API недоступен, данные сохраняются, компании продолжают создаваться и не захватывают адреса специалистов. Исправления company-read и registry остаются: нельзя восстановить прежнюю утечку revoked membership или удалить общую защиту адресов. После исправления точечно вернуть EXECUTE authenticated на эти три функции и повторить smoke.

Полный демонтаж схемы после появления пользовательских данных — отдельная миграция с экспортом/сохранением резервирования адресов и разрешением владельца. `DROP ... CASCADE` и автоматическое восстановление старых SQL-файлов не предусмотрены.
